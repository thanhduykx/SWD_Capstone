# CPMS Swagger Testing Guide

Use this guide when FE needs to test APIs manually through Swagger.

## Start Here

1. Run backend and open `http://localhost:5122/swagger`.
2. Open `00 - FE Test Guide`.
3. Call `GET /api/test-support/swagger-guide`.
4. Call `POST /api/auth/login`.
5. Copy `accessToken`.
6. Click `Authorize` in Swagger.
7. Paste the token value only.
8. Call protected endpoints.

The `api/test-support/*` endpoints are intended for local testing. They run in `Development` by default. Docker local testing enables them with `Swagger__ExposeTestSupport=true`; do not enable that flag for a real production deployment.

## Local Test Accounts

These accounts are for local development only.

| Role | Username | Password |
| --- | --- | --- |
| TrainingDepartment | `test.training` | `Test@123456` |
| Lecturer | `test.lecturer` | `Test@123456` |
| Lecturer | `test.lecturer.nodept` | `Test@123456` |
| Student | `test.student` | `Test@123456` |

Moderator is the main operator for account management. `SystemAdministrator` is kept only for compatibility with old local data and is not part of the normal FE test flow.

If one account is missing in a fresh database, login as moderator and create it through `POST /api/accounts`.

## Rules FE Should Not Guess

- Use GET APIs first to retrieve ids.
- `DateOnly` uses `yyyy-MM-dd`.
- `DateTime` uses ISO format, for example `2026-06-15T00:00:00Z`.
- Review `dayOfWeek` uses Monday=1 through Saturday=6.
- Review slots use 1 through 5. Defense slot rules are managed separately.
- A group leader must submit exactly five distinct student-availability slots.
- Lecturer availability is scoped to one review round. Moderator only sees it after submission with `POST /api/review-availability/week/submit?roundId={roundId}`.
- Account username is generated by backend from `fullName` and `identityCode`.
- Example: `Dương Thành Thanh Duy` + `SE194673` becomes `DuyDTTSE194673`.
- Lecturer account creation does not require `department`.
- TrainingDepartment account creation still uses `department` as the office/department name.

## Recommended Test Flows

### Account Flow

1. Login as `test.training`.
2. Authorize Swagger.
3. Call `GET /api/accounts`.
4. Call `POST /api/accounts`.
5. Login as the new account to verify credentials.

### Lecturer Availability Flow

1. Login as moderator and create/open the review round.
2. Login as `test.lecturer` and authorize Swagger.
3. Obtain the open `roundId` from the moderator's review-round response.
4. Call `PUT /api/review-availability/week?roundId={roundId}` to save a draft.
5. Call `POST /api/review-availability/week/submit?roundId={roundId}`.
6. Call `GET /api/review-availability/week?roundId={roundId}`.

### Student Availability Flow

1. Login as the student marked `isLeader=true` for a capstone group.
2. Call `GET /api/student-review/rounds` and select an `Open` round.
3. Call `PUT /api/student-review/slots` with exactly five distinct `{ dayOfWeek, slot }` values.
4. Call `GET /api/student-review/slots?roundId={roundId}` to verify the saved selection.
5. A non-leader, a sixth/fewer slot selection, or a non-Open round is rejected.

### Group Excel Import

Call `POST /api/import/groups` as `TrainingDepartment` or `SystemAdministrator` using multipart form data:

- `file`: `.xlsx` group list.
- `lecturerId`: supervisor profile ID; use IDs returned by `GET /api/review-scheduling/board`.

Only these Excel columns are imported: `Tên dự án (có thể trùng tên nhóm)`, `Họ & Tên`, `MSSV`, `Email (email trên FAP của SV)`, and `Họ & Tên Leader`. Other columns are ignored. Each project begins on a row containing a project title; following student rows with an empty project title belong to that project. The leader name must match exactly one student in the group.

### Review Scheduling Flow

1. Login as `test.training`.
2. Authorize Swagger.
3. Close the round with `PATCH /api/review-scheduling/rounds/{roundId}/status`; all active groups must already have five slots.
4. Call `GET /api/review-scheduling/board`.
5. Call `POST /api/review-scheduling/random-assign` for automatic scheduling, or `POST /api/review-sessions/bulk-assign` for manual scheduling.
6. Verify that every assignment is inside the group's five slots and a submitted lecturer slot. One panel/session contains at most three ordered groups.
7. Call `POST /api/review-schedules/publish` when every active group is assigned. Draft assignments are not visible and do not send email.
8. Publish is idempotency-protected and sends schedule email to assigned lecturers and group leaders.

### Review Checklist Flow

1. Login as assigned lecturer.
2. Call `GET /api/review-sessions/my`.
3. Use returned `submissionId`.
4. Call `GET /api/review-submissions/{submissionId}`.
5. Save with `PUT /api/review-submissions/{submissionId}/draft`.
6. Submit with `POST /api/review-submissions/{submissionId}/submit`.
7. Submit attendance with `POST /api/review-attendance/{sessionId}` and the assigned `groupId`.
8. Add reviewer feedback with `POST /api/review-attendance/{sessionId}/comments`.
9. Complete the group's review with `POST /api/review-attendance/{sessionId}/groups/{groupId}/complete` after all attendance and reviewer submissions exist.

### Defense Flow

1. Login as `test.training`.
2. Create defense round.
3. Create defense board.
4. Assign project to board.
5. Login as an assigned lecturer.
6. Resolve defense session.
7. Chairman starts scoring.
8. Council members submit scores.
9. Chairman closes scoring.
